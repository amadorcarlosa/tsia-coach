Foundry and Agent Framework model experiments

A dated record of the endpoint experiments, authentication design, embedding verification, typed deployment catalog, model capability research, and frontend-facing model API built for TSIA Coach.

Current outcome

The experiments established a practical boundary: Foundry chat models use the project endpoint through AIProjectClient, while raw embeddings use the Azure OpenAI resource endpoint through AzureOpenAIClient. Both clients reuse the same TokenCredential. A typed, static deployment catalog is now exposed to the frontend at GET /api/models.

one TokenCredential ├── AIProjectClient ──▶ Foundry project endpoint ──▶ AIAgent responses └── AzureOpenAIClient ──▶ Azure OpenAI endpoint ──▶ embedding vectors

The Foundry project endpoint does not currently expose raw embedding generation through AIProjectClient. The separate embedding endpoint is an Azure service boundary, not a failure of the application abstraction.

Verified C# agent and embedding flow

AIAgent agent =
    new AIProjectClient(
        new Uri(projectEndpoint),
        tokenCredential)
    .AsAIAgent(
        model: FoundryDeploymentCatalog.DeepSeek.V4Pro.Value,
        name: "TestAgent",
        instructions: "You are a helpful assistant. Be concise.");

var response = await agent.RunAsync(
    "What are three places to visit in Tegucigalpa?");

IEmbeddingGenerator<string, Embedding<float>> embeddingGenerator =
    new AzureOpenAIClient(
        new Uri(azureOpenAIEndpoint),
        tokenCredential)
    .GetEmbeddingClient(
        FoundryDeploymentCatalog.Embeddings.Small3.Value)
    .AsIEmbeddingGenerator();

ReadOnlyMemory<float> vector =
    await embeddingGenerator.GenerateVectorAsync(response.Text);

Console.WriteLine($"Embedding dimensions: {vector.Length}");
// Verified output: Embedding dimensions: 1536

AsIEmbeddingGenerator() is an adapter from the concrete OpenAI EmbeddingClient to the provider-neutral Microsoft.Extensions.AI.IEmbeddingGenerator<string, Embedding<float>> abstraction.

Authentication by environment

The application models credential selection as a C# discriminated union. Downstream clients receive only a TokenCredential and do not need to know how it was obtained.

public sealed record LocalDevelopment;
public sealed record ManagedIdentity(string ClientId);
public sealed record FederatedWorkloadIdentity(
    string TenantId,
    string ClientId,
    string TokenFilePath);

public union CredentialEnvironment(
    LocalDevelopment,
    ManagedIdentity,
    FederatedWorkloadIdentity);
EnvironmentCredentialUse
Local developmentAzureCliCredentialUses the developer's explicit az login session.
Azure hosted workloadManagedIdentityCredentialUser-assigned managed identity selected by client ID.
OIDC workloadWorkloadIdentityCredentialFederated tenant, client, and projected token file.

An uninitialized union should throw InvalidOperationException. Credential construction itself does not return null; authentication failures occur when the client requests a token.

Aspire configuration

The Aspire CLI syntax for AppHost user secrets is:

aspire secret set "azure-openai-endpoint" "https://GPrade.openai.azure.com/"
aspire secret get "azure-openai-endpoint"
aspire secret list
aspire secret path

An endpoint is normally configuration rather than sensitive data. API keys are secrets; Entra-based local development does not require an API-key secret. Aspire parameters must be mapped into the Server resource when the Server expects environment variables.

Typed deployment catalog

The catalog is a curated application allow-list. Nested static members preserve progressive IntelliSense, while descriptors carry metadata used by the frontend.

public sealed record FoundryDeploymentDescriptor(
    FoundryDeploymentName Name,
    string ModelName,
    string ModelVersion,
    string DisplayName,
    ModelProvider Provider,
    ModelLifecycle Lifecycle,
    IReadOnlyList<ModelApi> SupportedApis,

    IReadOnlyList<ModelModality> OutputModalities,
    IReadOnlyList<ModelFeature> Features,

FoundryDeploymentName provides semantic type safety. Constructor validation can reject empty strings, but only an Azure lookup or invocation can prove that a deployment currently exists.

Capability taxonomy

Operations, modalities, features, and interaction modes are separate dimensions. A live voice agent, for example, is chat with audio input, audio output, and realtime interaction.

public enum ModelApi
{
    Responses,
    ChatCompletions,
    Embeddings,
    AnthropicMessages,
    Realtime,
    Audio
}

public enum ModelOperation
{
    Chat,
    Embedding,
    SpeechToText,
    TextToSpeech
}

public enum ModelModality
{
    Text,
    Image,
    Audio,
    Video
}

public enum ModelFeature
{
    ToolCalling,
    StructuredOutput,
    Reasoning,
    FileInput,
    ComputerUse,
    JsonOutput
}

public enum InteractionMode
{
    RequestResponse,
    Streaming,
    Realtime
}

ModelApi answers which protocol surface can invoke the model. It is a separate dimension from what the model does (ModelOperation), what data it accepts (ModelModality), what additional capability it has (ModelFeature), and how responses are delivered (InteractionMode). JsonOutput means JSON can be returned. StructuredOutput means a supplied JSON Schema can be enforced. They are not interchangeable.

Capability metadata has three evidence levels: Azure account inventory, published model-card documentation, and a successful request against the exact deployment. The application catalog should not claim untested capabilities merely because a model family usually supports them.

A file type is not automatically a model modality, and an API feature is not automatically supported by every model available through that API. Azure processes PDFs by extracting text and rendering pages as images. PDF is therefore a supported file format (gated by FileInput), not a fundamental model modality.

Frontend model endpoint

The ASP.NET Core route group now exposes the configured catalog at GET /api/models.

public static RouteGroupBuilder MapModels(
    this RouteGroupBuilder group)
{
    group.MapGet("/models", () =>
    {
        FoundryDeploymentResponse[] models =
            FoundryDeploymentCatalog.All
                .Select(deployment => deployment.ToResponse())
                .ToArray();

        return TypedResults.Ok(models);
    })
    .WithName("GetModels")
    .WithTags("Models");

    return group;
}
var api = app.MapGroup("/api");
api.MapModels();

The frontend uses id as the deployment selection value. The server should resolve that value against FoundryDeploymentCatalog.All before invoking Foundry, preventing arbitrary model identifiers from being forwarded.

Architectural decisions

ConcernDecisionReason
Provider SDK differencesKeep provider-neutral domain metadata, but use the correct concrete service client.Agent responses and embeddings have different Azure endpoints.
AuthenticationResolve once to TokenCredential.The same credential can be reused by both Azure clients.
Deployment selectionStatic typed catalog and server-side allow-list.Stable IntelliSense, controlled frontend choices, and protection against arbitrary IDs.
CapabilitiesSeparate API surface, operation, modality, feature, and interaction mode.API protocol, chat operation, image input, tool use, and realtime transport describe different dimensions.
Simple labelsEnums.Labels carry no variant-specific data.
Variant-specific configurationDiscriminated unions when needed.Useful when variants carry different values, as credential environments do.
Deployment versus model identityStore both.Deployment aliases can point to different underlying model names and versions.

Verification status levels

Capability metadata has three evidence levels. The application catalog should track which level supports each claim.

LevelMeaningEvidence
DocumentedPublished model-card or Microsoft documentation claims support.Reference URL or page title.
Deployment-testedA successful request against the exact Foundry deployment confirmed the behavior.Date and test description.
UnverifiedNeither documentation nor a live test supports the claim.Absence of evidence.

  3. Smoke-test Claude through the project endpoint and native Anthropic endpoint.
  4. Test image input, structured output, tool calling, and streaming against exact deployments.
  5. Add embedding-specific metadata such as dimensions and token limits without forcing it onto chat descriptors.
  6. Compare existing knowledge retrieval with small embeddings, large embeddings, and a hybrid approach.
  7. Define retirement criteria for deprecated, legacy, preview, and duplicate deployments.
